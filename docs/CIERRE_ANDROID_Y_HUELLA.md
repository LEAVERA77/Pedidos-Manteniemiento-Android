# Cierre Android y acceso biométrico

## Operación

Para técnico/supervisor en la app Android se habilita el cierre solo de pedidos asignados a ese usuario que estén **En ejecución**. El cliente comprueba al abrir y al confirmar; la actualización SQL normal incluye una condición de estado y verifica que se haya modificado una fila. Si cambió el estado en servidor, muestra error y no marca cierre exitoso. En incidencias se filtran los cierres masivos, la API recibe una condición de estado y no se cierra la incidencia si quedaron pedidos abiertos no seleccionables. Web y administradores mantienen sus reglas anteriores.

Offline, el cierre de un pedido ya existente y en ejecución se guarda en la cola con condición de estado. Si al sincronizar la condición no coincide, permanece pendiente para revisión, no se descarta automáticamente. Una interrupción tras escribir pero antes de recibir respuesta también puede dejar una operación pendiente: resolver manualmente mediante procedimientos autorizados; no borrar la cola a ciegas. Un pedido creado localmente `off_` debe sincronizarse antes de cerrarse: el sistema anterior no vincula de forma fiable la inserción local con un cierre posterior.

Estas reglas protegen el **flujo actualizado**, no todos los accesos: el gateway SQL genérico, API sin la condición solicitada, clientes antiguos y acceso directo pueden eludirlas. La revisión de pedidos restantes de una incidencia usa la lista cargada, no una transacción que impida agregar otro pedido simultáneamente; una carrera puede dejar incidencia cerrada con pedidos abiertos. La identidad Android detectable en el cliente es manipulable. No constituye autorización integral en servidor ni protección frente a clientes adversarios. Un enforcement completo exige migrar el cierre a operación autenticada y retirar/cerrar las vías alternativas. El estado en caché offline puede estar desactualizado.

## Huella

Si hay acceso biométrico guardado, al iniciar el documento de la app se presenta el login y se abre automáticamente el diálogo de huella, siempre que la APK tenga soporte, haya acceso guardado y el sensor esté disponible en lugar de restaurar silenciosamente la sesión local; se conserva la cola offline y se puede ingresar manualmente. El botón de huella se mantiene visible con credencial guardada incluso si el sensor no está disponible temporalmente. Tras confirmación nativa, la credencial se entrega al login en memoria, **sin rellenar los campos visibles de usuario ni contraseña**. No se vacía la credencial biométrica por cambio normal de versión de APK; se conserva la validación de instalación y ámbito. Cambios de cuenta/tenant y recuperación pueden requerir volver a configurarla.

La huella aquí es una comodidad local, no MFA de administrador ni autenticación resistente a un dispositivo comprometido. La credencial nativa continúa en preferencias privadas sin cifrado de aplicación; esta etapa no implementa Android Keystore. La contraseña todavía pasa por la memoria de WebView/JavaScript y a la API al autenticar. Un APK antiguo conserva su comportamiento anterior hasta actualizarse; una reinstalación, pérdida de datos, sensor no disponible o cambios de credenciales pueden obligar al ingreso manual. La reanudación desde segundo plano y las interrupciones de cámara/huella deben probarse físicamente.

## Pruebas y despliegue

La APK carga GitHub Pages: actualizar API/web y Android de manera coordinada. Antes de la nueva web, el puente nativo nuevo no encontrará `__gnLoginConHuella` y debe permitir login manual; APK anterior puede seguir rellenando campos. Si Pages se actualiza antes que Render, el filtro de cliente funciona, pero la comprobación atómica solicitada por el cierre masivo no está disponible hasta desplegar API; evitar cierres masivos durante esa ventana. Verificar salud de Render y paridad. Se necesita nueva APK firmada con la misma identidad y prueba de actualización; no borrar almacenamiento ni cola.

En teléfono real: verificar apertura y reabrir, huella correcta/cancelada/sensor no disponible y reintento, fallback manual, usuario/contraseña nunca visibles, cambio de versión con huella guardada, y modo offline. Probar técnico y supervisor con pedidos asignados en Pendiente, Asignado, En ejecución y Cerrado; otro técnico; web; cierre masivo con mezcla; estado modificado por otro operador; encolar offline y sincronizar cuando el servidor ya cambió. Probar también incidencia parcialmente abierta, teléfono lento y cola existente. Playwright con puente simulado no sustituye BiometricPrompt ni una APK real. No solicitar secretos ni contenido de colas.


## Huella automática al volver de segundo plano

Tras iniciar sesión manualmente y aceptar guardar el acceso con biometría, la APK nueva solicita la huella al iniciar, sin pulsar el botón. Al volver de segundo plano a una sesión activa, una pantalla nativa cubre la vista y solicita huella; si se valida se continúa sin reiniciar la vista ni repetir el login. Si se cancela, permite reintentar o elegir usuario y contraseña. Para entrar manualmente se confirma el cierre de sesión: podría perderse un formulario no guardado, pero la cola offline no se borra. Sin acceso biométrico guardado o con el sensor no disponible se conserva el login manual. La huella no se configura sin consentimiento.

También puede pedirla al volver de cámara o selector de archivos, porque son actividades externas; verificar en el equipo que conserve los resultados y los formularios. No se reitera automáticamente tras una cancelación en la misma apertura. Android debe pasar al estado detenido para detectar el regreso; interrupciones parciales que no detienen la actividad no se consideran un nuevo ingreso. La APK se incrementó a versión 1.0.43 / 43. La interfaz nueva detecta el puente nativo actualizado y no activa el autoarranque en APK anteriores. La web cargada por APK anterior puede seguir con el botón manual hasta que se actualice.

**Validación nativa pendiente:** pruebas E2E simulan el puente y el análisis de Java solo comprueba sintaxis. Sin SDK/dispositivo no se ha compilado ni ejecutado BiometricPrompt, onStop/onResume, overlay o retorno de cámara real. Probar en dispositivo antes de distribuir; verificar instalación sobre APK anterior con la misma firma, huella previamente guardada, acceso inicial, cancelación y fallback, abrir/cerrar y bloquear/desbloquear, cámara/archivos, suspensión prolongada y offline. No considerar este overlay un mecanismo de seguridad independiente del resto del sistema ni garantía contra dispositivos comprometidos.
